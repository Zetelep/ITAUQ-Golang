# Taste
- Values clean code free of static-analysis/IDE warnings: flags self-assignments and dead code (e.g., `x.CreatedAt = x.CreatedAt`) and expects them removed rather than tolerated, including the unused imports or placeholder workarounds that such code can mask. Confidence: 0.7
- Prefers environment-driven configuration over hardcoded values: explicitly asked that hardcoded CORS origins be replaced with a `CORS_ALLOWED_ORIGINS` env var (comma-separated list). Confidence: 0.85
- Uses Postman for manual API testing; wants ready-to-import Postman collection examples (complete with collection variables, test scripts that auto-capture IDs, and error-case requests) rather than plain curl-style snippets. Confidence: 0.8
- Gives terse, high-level feature requests (e.g., "create the api endpoint for X feature") and expects the assistant to infer requirements and mirror the existing layered architecture (domain → repository → usecase → handler → route) plus previously built feature patterns (e.g., ownership checks via parent resource, nested CRUD routes, in-memory + postgres repo pair) without asking for clarification. Confidence: 0.7
- Expects work verified before hand-off: run `go build ./...` + `go vet ./...`, then `gofmt` check — fixing formatting only in newly created files and leaving pre-existing unformatted files untouched — plus a quick server smoke test (run in background) to confirm startup. Confidence: 0.65
- Implements endpoint features strictly against the checked-in API_SPECIFICATION.md: exact status codes (201 on create, 204 on delete), documented auth rules (owner-only for mutations, super-admin allowed on reads), and correct HTTP mapping of domain errors (e.g., sentinel validation errors returned as 400 rather than leaking as 500). Confidence: 0.6
- Keeps `docs/API.md` in sync with implemented features: after building an endpoint, expects every cross-referenced section updated — table of contents entry, a new endpoint section written in the exact format of existing sections (auth, params, request/response examples, error lists), role permission matrix rows, env var documentation, Postman collection/variable lists, architecture directory tree, and removal of the item from the "Planned Endpoints" list. Confidence: 0.85
- Prefers the assistant to flag real spec ambiguities rather than silently guess: when an API_SPECIFICATION.md detail (e.g., response shape: raw nested JSON vs flattened parsed struct) has multiple defensible interpretations, the assistant should implement a reasonable default but explicitly call out the ambiguity at hand-off and let the user pick. Confidence: 0.7
- References files in chat using `@` prefix (e.g., `@API_SPECIFICATION.md`, `@db.sql`, `@pkg\sus\sus.json`) to point the assistant at specific files in the workspace, rather than pasting file contents or describing them in prose. Confidence: 0.85
- Edits spec/schema files themselves between sessions ("i already updated the @API_SPECIFICATION.md and @db.sql") and expects the assistant to trust the new spec state, only updating endpoints/handlers/db migrations that are genuinely affected by the change — not rewriting the spec or touching unchanged endpoints. Confidence: 0.8
